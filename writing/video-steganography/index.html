Hiding Messages in Moving Video Objects

Revisiting my bachelor’s final project: object tracking, transform-domain embedding, error correction, and what I would redesign today.

September 9, 2026

During my bachelor’s degree, I worked on a video-steganography prototype in MATLAB. The central idea was to hide a message inside the visual content of a video while keeping the change difficult to notice. Rather than treating every pixel in every frame as an equal carrier, the design first identifies moving objects and then uses a tracked object region for transform-domain embedding.

Revisiting the repository years later is useful for two reasons. It connects ideas from computer vision, signal processing, coding theory, and video processing in one pipeline. It also shows the difference between demonstrating individual algorithms and integrating them into a reproducible end-to-end system.

The complete source is available in the video-steganography repository.

The problem the project explored

Cryptography makes a message unreadable without a key. Steganography addresses a different problem: concealing that a message is present at all. A media file can act as the carrier, but changing it creates a tradeoff among three goals:

  • Imperceptibility: the modified video should look close to the original.
  • Capacity: the carrier should hold a useful amount of information.
  • Robustness: the message should survive noise, compression, or other changes.

My prototype explored this tradeoff by selecting a moving region, encoding the payload, and modifying frequency coefficients instead of directly replacing visible pixel values.

How the repository is organized

Code Responsibility
main.m Orchestrates frame loading, region selection, payload preparation, embedding, video writing, and recovery experiments.
mot_track.m Detects foreground objects and maintains multiple tracks with Kalman filters.
Data_Extracting_Stage.m Processes the output video, records bounding boxes, and experiments with recovery-side tracking.
sec_Msg.m Converts text to bits and applies key-mixing and error-coding experiments.
embedded_DWT.m Embeds data by modifying coefficients from a two-dimensional Haar wavelet transform.
wtmark.m and exwmark.m Embed and recover a binary watermark through block-based discrete cosine transforms.

1. Finding a carrier with object tracking

The tracking path begins with a Gaussian-mixture foreground detector. Each frame is converted into a binary foreground mask, after which morphological opening removes small noise, closing joins nearby foreground regions, and hole filling produces more coherent shapes. Blob analysis then returns the centroid and bounding box of each sufficiently large region.

In mot_track.m, every active track stores an identifier, a bounding box, a Kalman filter, its age, and visibility counters. The code predicts where each object should appear in the next frame, computes assignment costs between predictions and new detections, updates matched tracks, creates tracks for unmatched detections, and removes tracks that remain invisible for too long. Short-lived detections are excluded from the displayed reliable tracks.

This tracking layer provides the conceptual link between ordinary image watermarking and video steganography: a stable bounding box can identify the same potential carrier as it moves through the scene. In main.m, precomputed bounding boxes from a1.mat are used to crop regions from a sequence of frames before embedding begins.

2. Turning a message into an embeddable payload

sec_Msg.m trims the input text, converts each character to an eight-bit representation, and flattens the result into a bit vector. The bits are grouped in blocks of four and passed through a Hamming (7,4) encoder, which adds redundant bits so that a single-bit error in a codeword can be corrected. The encoded values are then mixed with a generated key through XOR operations before being returned to the embedding functions.

The file also constructs BCH-related objects, but the resulting BCH codeword is not connected to the value returned by the function. The most precise description of the implemented payload path is therefore Hamming coding plus experimental key mixing, with BCH present as an unfinished experiment.

The comments in the original code use the word encryption. The XOR-based operations should not be treated as modern cryptographic protection. A production design would first use an authenticated encryption scheme with explicit key management, and then apply error correction to the resulting ciphertext.

3. The Haar DWT embedding path

embedded_DWT.m applies a two-dimensional Haar discrete wavelet transform to the selected image region. The transform splits the image into four coefficient bands: LL, LH, HL, and HH. These describe low-frequency image structure and horizontal, vertical, and diagonal detail at the selected scale.

The prototype selects the LL band, reshapes its coefficients, and adjusts them using a three-bit quantization pattern derived from the payload. It then performs an inverse wavelet transform with the unchanged detail bands to reconstruct the spatial image. Embedding in a low-frequency band can improve persistence, but changes there can also be more visually noticeable. That choice is therefore part of the robustness-versus-imperceptibility tradeoff that should be measured experimentally.

4. The block DCT embedding path

wtmark.m explores a separate frequency-domain method. It converts the carrier to grayscale, resizes it to 512 by 512 pixels, divides the transformed image into 8 by 8 blocks, and resizes the binary watermark to 32 by 32 values. One watermark bit is represented in each of the first 1,024 blocks by adding or subtracting 35 from the coefficient at position (8,8).

After modifying the coefficients, the function performs the inverse block transform and calculates the peak signal-to-noise ratio between the original and embedded images. exwmark.m reverses the process by transforming the blocks again, reading the sign of the same coefficient, and reconstructing the 32 by 32 watermark.

This branch captures a classic watermarking idea: lower-frequency coefficients tend to be more robust but more visible, while high-frequency coefficients tend to be less visible but more vulnerable to compression and noise. The hard-coded coefficient and strength provide a starting point for experiments rather than a universally optimal setting.

5. Where the prototype stops short of end-to-end integration

The most important finding from rereading the code is that the individual stages are not fully connected in the checked-in version. main.m computes DWT and DCT embedded regions, but the video-writing loop writes the original values from images. It does not paste either transformed region back into its tracked bounding box before creating myStego.avi. The later recovery code consequently mixes video-processing experiments with recovery performed against in-memory transformed data.

The repository also expects local inputs such as View_001, a1.mat, and a subfile directory that are not checked in. Some helper paths are incomplete, and several APIs, including blkproc and im2bw, reflect the MATLAB version used at the time. The repository is therefore best read as a bachelor’s research prototype containing working algorithmic components, not as a turnkey steganography package.

How I would rebuild it today

I would preserve the original research question while making the boundaries between stages explicit and testable:

  1. Decode the video and attach frame numbers and timestamps to every frame.
  2. Detect and track candidate objects, then select tracks using duration, size, texture, and motion stability.
  3. Frame the payload with a version, length, checksum, and deterministic error-correcting code.
  4. Encrypt the payload with authenticated encryption when confidentiality is required.
  5. Embed bits across selected transform coefficients and record the exact capacity used.
  6. Paste each modified region back into its original frame before encoding the output video.
  7. Run extraction independently from the produced file, without sharing in-memory embedding state.
  8. Measure PSNR, SSIM, payload bit-error rate, and recovery after compression, noise, resizing, and dropped frames.

I would also replace fixed frame and bounding-box indices with configuration, seed every randomized operation for reproducible experiments, retain intermediate artifacts, and add tests for each transform and encode/decode round trip. A small command-line interface could then connect the stages without hiding their parameters.

What I take from the project now

This project was an early attempt to combine several technical domains inside one system. The most valuable lesson is that an algorithm working in isolation is only one part of engineering. Data contracts between stages, reproducible inputs, evaluation metrics, and independent end-to-end tests determine whether the complete system works.

That lesson still shapes how I approach software and machine-learning systems today: understand each component deeply, but validate the behavior at the boundaries where those components meet.
